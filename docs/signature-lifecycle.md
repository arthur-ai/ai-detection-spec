# Tracking signatures as agents evolve

An identifier is a fact about one build of one product on one machine. Products change theirs.
This repo has already been bitten twice:

- **`bot.molt.mac`** shipped for OpenClaw, straight from the vendor's own Homebrew metadata. It
  matched nothing on any Mac. The real identifier is `ai.openclaw.mac`, and only installing the
  thing revealed it.
- **`aider`** installs as `aider-chat` under `uv` and `pipx`, while its state directory is
  `~/.aider`. Evidence and signature never met, and nothing errored.

Both were silent. Neither was caught by review. The question this document answers is how to
keep a catalog true as the things it describes change underneath it.

## What the field does

| | Mechanism | What it is good at | What it does not solve here |
|---|---|---|---|
| **Sigma** | a `status` field — `experimental` → `test` → `stable` → `deprecated` — driving CI promotion | making maturity explicit, so automation can refuse to deploy an unproven rule | maturity is asserted by an author, not measured |
| **Jamf Patch Management** | versioned *software title definitions*, per-version attributes, centrally maintained | version-aware identity, professionally curated | central curation is the product. We are the curator |
| **AutoPkg** | `verify-trust-info`: a hash over the recipe and its processors. Upstream change **invalidates trust and blocks the run** until a human reviews the diff | *drift blocks by default* — the strongest idea here | trusts a hash of inputs, not an observation of output |
| **Homebrew** | `livecheck` detects new upstream versions and autobumps; casks pinned `version :latest` are **excluded from autobumping** | automation against upstream, and an explicit list of what cannot be tracked | tracks versions, not identifiers |
| **CPE** | centrally assigned product names, NVD's key | one authority, universally referenced | *"you cannot always derive a CPE from the product itself"* — you consult a dictionary |
| **PURL** | identifiers **derived from package metadata**, decentralised, with `vers` for version ranges | derivable, no authority, ranges rather than points | only covers package-manager-distributed things |

**The two that matter for us are AutoPkg and PURL.** Our identifiers are already PURL-shaped —
a bundle id, an npm name, an extension id and an image repository are all *derivable from the
artifact*, needing no registry to look up. And AutoPkg answers the maintenance question the
right way round: drift should **stop the build**, not appear in a report nobody reads.

Sigma's `status` is worth borrowing in one respect and rejecting in another. Explicitly grading
confidence is right. Letting an author *assert* the grade is what we should not copy: this repo
grades by evidence, and the evidence already exists — the scenario suite installs real software.

## The design

Three layers, and the first one does not change.

### 1. The matcher's input stays flat

`catalog/agents.yaml` keeps its shape. Matching must not need to know about versions or
environments, because the endpoint does not know them either: a `bundle_ids` row carries an
identifier and a version string that mean different things per route, and an `ext` row carries
neither reliably.

```yaml
- id: ollama
  bundle_ids: [com.electron.ollama]
  images: [ollama/ollama]
```

An identifier observed for one version almost always still matches the next. Version binding
belongs in provenance, not in matching — the same reason PURL puts ranges in a qualifier rather
than in the name.

### 2. Observations, generated by the tests

A record per **(agent, identifier, version, environment, install route)**. Not hand-written:
hand-maintained provenance rots, and this repo's standing rule is that identifiers are facts
read off real installs. The scenarios already perform those installs; they simply do not record
what they saw.

```yaml
# catalog/observations/ollama.yaml   — appended by a scenario run, reviewed in the PR
- identifier: {route: bundle_ids, value: com.electron.ollama}
  agent_version: "0.12.3"
  environment: {os: "26.6.2", arch: arm64}
  install: homebrew-cask:ollama-app
  observed_at: 2026-08-31
  source: scenario/30-local-models
```

**Multiple install paths for one version on one environment are multiple observations**, which
is the natural shape rather than a special case. A single agent version routinely arrives as a
cask *and* an npm global *and* a `curl | bash` installer, and each can produce a different
identifier — that is the whole reason the catalog has routes.

Environment is a dimension, not a footnote. `chrome_extensions` behaves differently per browser
channel; a bundle id can differ between an Intel and an Apple Silicon build; an installer can
place a binary somewhere else on a managed Mac.

### 3. Gates, so drift stops the build

| Gate | Rule | Failure means |
|---|---|---|
| **Verified** | every identifier in `agents.yaml` has ≥1 observation, or an explicit `unverified` entry | a signature nobody has ever seen work |
| **Catalogued** | every observed identifier appears in `agents.yaml` | **drift** — the product changed and we now know |
| **Fresh** | warn when an identifier's newest observation is older than N days, or when a newer agent version was observed without re-confirming it | the signature may already be dead |

The middle gate is the AutoPkg move. A scheduled run installs current versions; if Cursor
changes its bundle id, the scenario observes the new one, the gate fails with *observed but not
catalogued*, and a human decides whether to add it as an alias or replace it. Drift becomes a
red build on a Tuesday rather than a fleet reporting zero Cursor installs for six months.

### 4. What cannot be verified, listed explicitly

Homebrew excludes `version :latest` casks from autobumping because they cannot be tracked, and
says so. The same honesty is required here, because the alternative is a catalog where verified
and assumed identifiers are indistinguishable.

```yaml
unverified:
  - identifier: {route: bundle_ids, value: com.example.enterprise-agent}
    reason: requires a paid licence and an interactive sign-in; no unattended install
    evidence: vendor documentation
    raised: 2026-08-31
```

`evidence` grades what we actually have, weakest to strongest:

| grade | meaning |
|---|---|
| `vendor-documentation` | what produced `bot.molt.mac`. Lowest trust |
| `registry-manifest` | the artifact resolves under that exact name from its registry |
| `artifact-metadata` | the artifact's own config confirms what it is — an image entrypoint, a bundle `Info.plist` |
| `real-install` | observed in `docker_images`, `apps`, `chrome_extensions` on a machine |

**This is now implemented**, and slightly stricter than sketched above: the gate does not
merely permit an exception, it *requires* one. `tools/validate_catalog.py` refuses an agent
that is neither covered by a scenario nor carrying an `unverified` block, and refuses the
block itself if the reason is too short to be a reason, the date is not a date, the grade is
not one of the three, or the agent is in fact already covered — in which case the block
contradicts the scenario and one of them is stale. `docs/agents.md` renders the register on
every regeneration.

The gate **permits** an unverified entry and **reports it every run**, so it cannot quietly
become permanent. A catalog is allowed to carry a guess. It is not allowed to hide one.

## Why not the alternatives

**Version-keyed identifiers in the catalog** — `bundle_ids: {">=1.4": [...]}`. The endpoint
does not reliably know an agent's version at match time, and for `ext` and `image` rows it
never does. It would push a version-resolution problem onto the one component that must stay
simple.

**A separate signature feed, curated centrally** — Jamf's model. It is the right answer when
curation is the product you sell. Here it would add a distribution channel and a staleness
problem to a repo whose whole point is that the catalog is public, diffable and reviewed in a
pull request.

**Hashing inputs, AutoPkg-style, rather than observing outputs** — trust hashes catch *a recipe
changing*. Our failure is *the world changing while our file stays the same*, which a hash of
our own file cannot see.

## A stronger grade than observation, where the artifact allows it

The grades above run from *the vendor says so* up to *observed on a machine*, and observation
is normally the ceiling. For one route it is not.

A Chromium extension id is not assigned, it is **derived**: SHA-256 over the developer's DER
public key, first 16 bytes, hex mapped `0-f` to `a-p`. The Web Store's signed CRX carries
that key in its manifest. So the id can be recomputed from the publisher's own signed
artifact:

```console
$ curl -sL "https://clients2.google.com/service/update2/crx?response=redirect\
&prodversion=152.0&acceptformat=crx3&x=id%3D<id>%26uc" -o ext.crx
  manifest key present: True
  id derived from the key: fcoeoabgfenejglbffodgkkbkcdhcgfn
```

That is a different kind of claim from *we saw this id on a Mac*. An observation says one
machine reported it once; a derivation says the id belongs to that signing key and could not
belong to anyone else's. It also explains, exactly, why a planted extension reports an EMPTY
identifier — unpacked extensions carry no key, so there is nothing to derive from.

This is the PURL argument arriving at its conclusion. PURL beats CPE because an identifier
derivable from the artifact needs no registry to vouch for it; a key-derived extension id is
that property taken to its limit — the artifact does not merely *carry* its identifier, it
*proves* it. Where a route offers this, prefer it: it is cheaper than a VM scenario, it does
not decay when a vendor renames a product, and it cannot be faked without the signing key.

Most routes offer nothing like it. A bundle id is a string in a plist that anyone can write,
an image tag is chosen by whoever ran `docker tag`, and a Homebrew token is a name in a
repository. For those, a real install remains the bar.

## What was actually built, and how it differs

The design above is not a plan any more, and the differences are worth recording because
each was a decision rather than a drift.

| designed | built | why |
|---|---|---|
| `catalog/observations/<agent>.yaml` | `test/scenarios/<name>/observed.json` | the producer is a scenario RUN, so the file lives beside the thing that writes it. A run changes exactly one file, and a reviewer reads the diff next to the scenario that caused it |
| one record per (identifier, environment, install route), collapsed to `first_seen`/`last_seen` | one record per (agent, route, value) with `agent_version`, `os`, `arch` | no history is kept yet. The collapse solves a growth problem that does not exist at 42 identifiers, and inventing `first_seen` from a single run would date evidence we do not have |
| a **Fresh** gate warning on stale observations | **not implemented** | with no `first_seen`/`last_seen` there is no age to compare. An identifier can read *covered by CI* on the strength of a run from months ago, and nothing says so |

Two things the implementation added that the design did not anticipate, both because the
first version was wrong in a way only a real run exposed:

**Credits are keyed by (route, value), never by value alone.** OpenClaw ships an npm package
*and* a Homebrew cask both called `openclaw`, so a value-keyed credit let an npm-only scenario
record the Homebrew token as observed — a real install that no row supported.

**Coverage is counted against CI, not against "has anyone run this".** A scenario that passes
only on a maintainer's machine catches nothing on a pull request, and one scenario sat in
exactly that state: passing locally, absent from the matrix, indistinguishable from covered.

## The state that does the most work

`did not appear` — a CI scenario installed the agent and the identifier never showed up. It
carries more information than any other state because it means one of three things:

1. **the scenario installs by another route.** Fixable, and the fix is a separate scenario:
   two routes claiming the same binary name cannot share a machine.
2. **the artifact only exists once the agent runs.** A state directory is not created by
   installing.
3. **the identifier is wrong.** Nothing can produce it, because it names something else.

The third case is why this state earns its place. Both catalog bugs found so far surfaced
through it and neither survived a registry lookup: npm `mcp` is Mintlify's package, and npm
`aider` is a static-site component by an unrelated maintainer. Each sat beside a comment
explaining the discrepancy rather than questioning it — which is precisely how a guess
survives review, and exactly what an evidence grade cannot catch on its own.

## Scale

Three things grow, at very different rates, and only one of them is a problem.

**Identifiers: free, and measured.** The queries hold no identifiers, so the catalog does not
reach an endpoint and adding agents costs nothing on the wire. Verified rather than assumed:
growing `agents.yaml` from 21 agents to **221** left `dist/discovery.sql` byte-identical and the
framed payload unchanged at 17,868 bytes. Whatever limits this design, it is not how many agents
we can name.

**Matching: already the right shape, with one thing to watch.** Today's 21 agents give 55 exact
identifiers, 4 prefixes and 6 path globs. A row costs one dictionary lookup — O(1), and flat as
the catalog grows — *plus* a linear pass over the prefixes and, for `file` rows only, the globs.

So the exact routes scale indefinitely and the **prefix and glob routes do not**. Every
`launchd_prefixes` entry and every `state_dirs`/`binaries`/`model_stores` glob is compared
against every candidate row. At 500 agents that is a few hundred regexes per `file` row across
hundreds of rows. The rule that follows: **prefer an exact route; justify a glob.** If the glob
count outgrows the exact count, group them by first path component before matching rather than
scanning the whole list.

**Observations: the one that actually grows combinatorially**, at agents × versions ×
environments × install routes × runs. Append-only would be unbounded, so it is not append-only:

```yaml
- identifier: {route: bundle_ids, value: com.electron.ollama}
  environment: {os: "26.6.2", arch: arm64}
  install: homebrew-cask:ollama-app
  first_seen: {agent_version: "0.9.1", at: 2026-06-02, source: scenario/30-local-models}
  last_seen:  {agent_version: "0.12.3", at: 2026-08-31, source: scenario/30-local-models}
  runs: 47
```

One row per **(identifier, environment, install route)** — collapsed, not per run. `first_seen`
answers "since when", `last_seen` answers "is this still true", and the version range between
them is the useful fact rather than 47 near-identical rows. That bounds the file at the product
of dimensions that actually differ, and it is why the Fresh gate can be a cheap comparison
rather than a scan over history.

**File layout.** One `agents.yaml` is right while a reader can hold it in their head, and
`validate_catalog.py` already iterates whatever it is given. Past roughly a hundred agents,
split to `catalog/agents/<id>.yaml` — one file per agent makes a contribution a single-file diff
and stops every PR touching the same file, which is the review cost that bites first. The
matcher concatenates; nothing else changes. Observations split per agent from the start, because
they are machine-written and nobody reads them whole.

## Cost, stated plainly

Real installs are the expensive part and there is no way around them: the two bugs above were
each invisible to review and to synthetic fixtures. A VM scenario is ~10 minutes; the suite runs
on a schedule rather than per pull request for exactly that reason. This design does not make
verification cheaper. It makes the *absence* of verification visible, which is the part that
currently is not.
